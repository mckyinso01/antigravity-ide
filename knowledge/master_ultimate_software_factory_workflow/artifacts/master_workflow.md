# Master Ultimate AI Software Factory & Orchestrator Workflow Protocol

## Core Governance Directives

### 1. Mandatory 200+ Micro-to-Macro Asset & UI Element Scenarios Standard (50 per Asset/Component)
- **Zero-Bypass Scenario Audit**: For every software project, the Orchestrator MUST formulate at least 50 Exhaustive Scenarios per asset/component/tool/feature/capability (minimum 200 scenarios across 4 core components) before code drafting.
- **Explicit Micro-to-Macro Element Categorization**: Scenarios MUST be categorized into explicit micro UI asset targets:
  - **Category A: Buttons & Action Triggers** (Click feedbacks, hover states, spinners, disabled states, double-click prevention).
  - **Category B: Textareas, Input Fields & Keyboards** (Backspace clearability, multiline pasting, PII/secret regex interception, Rule 4.1 claims).
  - **Category C: Search Tools, Filter Tools & Dropdowns** (Ctrl+K search, fuzzy queries, tag selection, currency dropdowns).
  - **Category D: Views, Modals & Slide-Over Drawers** (Collapsible rails, fluid edge-to-edge viewports, backdrop Esc dismissals).
  - **Category E: Tooltips, Badges & Status Pills** (Pill status colors, SLA latency badges, hover tooltips).
  - **Category F: Toast Messages & Feedback Banners** (Alert banners, toast auto-dismiss, self-healing notifications).
  - **Category G: Backend Persistence & Crypto Ledgers** (LocalState caching, SHA-256 block chain append, ClickHouse MergeTree DDL deduplication).



### 2. Mandatory 18-Council, COPILOT-01 & MCP Invocation Protocol
- **Domain Council Cross-Examination**: Across every stage (Stage 1 through Stage 12), the Orchestrator MUST formally invoke and cross-examine with all 18 Domain Council Subagents (`SEC-01`, `FE-01`, `QA-01`, `ARCH-01`, `SRE-01`, `BI-01`, `UX-01`) and **`COPILOT-01` (Universal Multi-Role Micro-to-Macro Inspector & Production Clearance Co-Auditor)**.
- **MCP Server Invocation**: All registered MCP tools (`StitchMCP` for design systems & screen creation, `chrome-devtools-mcp` for visual audits, `firebase-mcp-server`, `alloydb-postgresql`, `neon`) MUST be executed in alignment with the validation gates of each stage.


### 3. Strict 70% Planning / 30% Coding Lock
- **NO PREMATURE CODING**: Writing React, HTML, CSS, or JS code before completing Stages 1–7 (Client Brief, Role-Play Pain Points, 18-Council Debate, Tools Matrix, 120 User Journeys, StitchMCP Design System, Modals Architecture) is STRICTLY PROHIBITED.
- **Mandatory Live Telemetry Badge**: Every turn MUST display:
  `📍 WORKFLOW TELEMETRY: [STAGE X: <STAGE NAME> — 🟡 ACTIVE / CLEARANCE REQUIRED]`

### 4. Mandatory Stage 9 Pre-Dispatch Evaluation & Compliance Audit Gate
- **Automated E2E Test Suite Execution**: Prior to declaring Stage 9 clearance or launching Stage 12 live outreach, the Orchestrator MUST execute an automated E2E compliance runner (`exhaustive_e2e_compliance_auditor.py`) verifying 100% Zero-Defect quality (HTTP 200 Surge Check, PBKDF2/Crypto logic, Sentinel contracts, SHA-256 block chain continuity, and Sub-10ms secret leakage regex interceptor).
- **Agentic AI Specific Safety Audit**: Verify HITL gating, PII redaction, prompt injection defense, and kill switch (<5s SLA) readiness.

### 5. Mandatory Recipient Identity & IMAP Bounce Verification Protocol
- **100% Recipient Identity Match**: The email dispatch target MUST be audited against `client_profile.json` to guarantee 0% recipient mismatch before firing SMTP packets.
- **Automated Post-Dispatch IMAP Bounce Audit**: Immediately following live SMTP delivery (`send_authenticated_gmail.py`), execute an automated IMAP inbox audit (`check_gmail_bounces.py`) to confirm zero bounce backs and guarantee 100% inbox landing.

### 6. Mandatory 3-Tier User Journey, Navigation Flow & State Machine Mapping Protocol
- **Stage 3 UX/UI Navigation & State Lock**: At Stage 3 (UX/UI Design & Information Architecture), the Orchestrator MUST explicitly define:
  1. Visual User Journey Navigation Flow (Mermaid Diagram)
  2. Component State Machine Specifications (`IDLE`, `LIVE`, `SCANNING`, `REDACTED`, `COMMITTED`)
  3. 3-Step User Lifecycle Mapping (*Trigger* ➔ *Feedback* ➔ *Outcome*) for 100% of interactive components.

### 7. Mandatory Stage 11 Deep Research Stage Protocol
- **Zero Blind-Spot Research Mandate**: Stage 11 is explicitly defined as a systematic **Deep Research Stage** replacing simple visual audits.
- **Scope of Research**:
  1. Integrations & Connectors (APIs, SDKs, Auth, Rate limits)
  2. Additional Features & Components (Feature gap analysis vs industry benchmarks)
  3. Assets & Dependencies (Schemas, configs, libraries, licenses)
  4. Journeys, States & Views (End-to-end mapping & UI audits)
  5. Exhaustive Testing (Functional, Integration, Performance, Security, Compliance)
- **Mandatory Outputs**: All outputs stored in `/research` folder (`research_integrations_and_connectors.md`, `research_feature_gap_analysis.md`, `research_asset_inventory.md`, `research_journey_state_view_maps.md`, `research_exhaustive_test_plan.md`, `final_deep_research_report.md`).

### 8. Mandatory Stage 12 Exhaustive Evaluation Stage Protocol
- **Formal Readiness Decision Gate**: Stage 12 consumes Stage 11 research/test artifacts to perform systematic evaluations across all 18 Councilors, `COPILOT-01`, and MCP servers (`StitchMCP`, `chrome-devtools-mcp`).
- **Scope of Evaluation**:
  1. Functional Evaluation (`eval_functional.md`)
  2. Integration Evaluation (`eval_integration.md`)
  3. Performance Evaluation (`eval_performance.md`: Soak, spike, chaos, HDR histograms p50/p90/p99/p999)
  4. Security & Compliance Evaluation (`eval_security_compliance.md`)
  5. User Journey Evaluation (`eval_journeys_views.md`)
  6. Macro & Micro Evaluation (`eval_macro_micro.md`)
- **Mandatory Outputs**: All outputs stored in `/evaluation` folder (`eval_functional.md`, `eval_integration.md`, `eval_performance.md`, `eval_security_compliance.md`, `eval_journeys_views.md`, `eval_macro_micro.md`, `final_go_no_go_decision.md`).

### 9. Mandatory Stage 13 Client Proposal Pitch & Delivery Protocol
- **Live Client Outreach Package**: Stage 13 produces `reddit_pitch_proposal.md` with 1-to-1 requirement matches, live Surge URL (`https://gatzdevs.surge.sh`), and standing by for user's explicit command before live SMTP dispatch.
